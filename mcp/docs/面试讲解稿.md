# 面试讲解稿：MCP / AI Agent 接入

> 用途：面试被问到"你说要把项目接入 AI Agent，做到哪一步了"时，照这个讲。
> 铁律：**能说做过什么，不能说做到了什么程度还没到的东西。**

---

## 一、三句话版本（30 秒，用于自我介绍收尾或被打断时）

> 我维护的开源应急响应工具集，现在做了一个 MCP Server：把排查经验封装成可被 AI Agent 调用的只读工具。
> 核心设计是**判定环节不放进模型**——告警进来走本地规则库做确定性匹配，模型只负责把人话翻译成查询、把结构化结果讲成人话。
> 返回值里"待人工确认"和"禁止自动处置"是**硬编码**的，不靠提示词约束。

---

## 二、五分钟版本（技术追问时展开）

### 1. 为什么做这个（30 秒）

> 我做应急响应排查时最大的痛点是：告警量大、重复劳动多，但**真正下结论的环节不敢外包**。
> 所以我想做的不是"AI 替我研判"，而是"AI 帮我把脏活干掉，结论仍然由确定性规则给、由人确认"。
> MCP 正好提供了这个分层——Server 给能力，模型在客户端侧只做翻译和表达。

### 2. 架构（60 秒，建议边画边说）

```
[用户] ←→ [模型 / MCP 客户端] ←→ [MCP Server: blue-team-ir]
                                      ├── triage.py   本地规则研判引擎（确定性）
                                      ├── guard.py    入参校验 + 审计日志
                                      └── rules/triage-rules.yaml  10 条规则（带 ATT&CK）
```

> 三层分工：**模型管表达，Server 管能力，规则管结论**。
> Server 不发起任何外部网络请求，也不调用任何大模型 API——这一条是刻意设计的，
> 离线环境（客户内网、只带 U 盘的现场）也能跑。

### 3. 两个工具（30 秒）

> - `triage_alert`：把一条告警丢进去，返回命中的规则、ATT&CK 编号、置信度、**误报提示**、**建议人工验证的步骤**。
> - `list_rules`：列出规则库覆盖范围——这个工具的作用是让模型知道能力边界，清单外的告警它会如实说"未命中"，不会瞎编。

### 4. 安全底线怎么落地的（90 秒，这段最有含金量）

> 我在设计文档里写了八条安全底线，这个版本把其中能代码化的都代码化了：
>
> | 约束 | 实现 |
> |---|---|
> | 只读 | 只暴露查询/研判类工具，没有任何命令执行或写操作接口 |
> | 白名单 | 入参用 `Literal` 枚举约束，非白名单值直接拒绝 |
> | 参数校验 | 长度上限 20000 字符、剔除控制字符；路径参数拒绝 `..` 和全部 shell 元字符 |
> | 审计 | 每次调用落盘 `audit/YYYYMMDD.jsonl` |
> | **人在回路** | `human_review_required=True`、`auto_action_allowed=False` **硬编码**，模型改不了 |
> | 能力边界 | `list_rules` 显式暴露覆盖范围，未命中如实说明 |
>
> 最后一条我想多说一句：我还在 Server 的 instructions 里明确要求模型
> **只能给"建议人工执行的验证命令"，不能输出删除文件、结束进程、隔离主机这类处置动作作为最终建议**。
> 因为应急现场判定错一次，代价是误处置或漏处置，而幻觉是概率性的，靠提示词压不到零——
> 所以我把"不下处置结论"这件事，做进了代码和返回值，而不是只写在提示词里。

### 5. 零依赖设计（30 秒）

> `triage.py` 和 `guard.py` 不依赖任何第三方包：有 PyYAML 用 PyYAML，没有就回退到我自己写的最小 YAML 解析器。
> 原因是应急现场经常离线、只有便携 Python，装不了包就跑不了的工具没有价值。

### 6. 现状与下一步（60 秒，诚实段）

> 现在的状态是 **v0.1.0 最小可用版**：10 条规则、2 个只读工具，本地自检跑通，可以通过 MCP Inspector 调用。
>
> 局限我也清楚：这是**关键词匹配 + 严重级别打分的初筛器，不是检测引擎**。
> 它解决的是"告警太多、先把明显的一类归拢出来"这个分诊问题，
> 解决不了免杀绕过和未知攻击——那需要行为分析和情报支撑。
>
> 下一步三步：① 接入真实日志源（Windows 安全日志、Linux auth.log/auditd），规则库扩到 30+；
> ② 把已有采集脚本封装成只读工具；③ 做效果评估——人工研判结论回流、规则迭代、复测，量化命中率和误报率。
> 第三步对应贵司 JD 里"Agent 效果优化"那条，我理解效果这事没有度量就没有优化。

## 三、诚实边界（**这张表比话术重要**）

| 能说 | 不能说 |
|---|---|
| "做了一个能跑的 MCP Server，本地自检通过" | "已经接入生产/Agent 已经在用" |
| "10 条规则，覆盖挖矿/WebShell/持久化等 10 类" | "规则库很全/能检出大部分攻击" |
| "通过 MCP Inspector 调用验证过" | "在客户环境验证过" |
| "下一步计划接入真实日志源并做效果评估" | "效果评估已经做完了" |
| "关键词匹配初筛器" | "检测引擎 / 有检测能力" |
| "不调用大模型 API，判定是确定性的" | "用了大模型做研判" |

被追问到不会的，统一句式：

> "这块我目前只做到 X 的程度，再往下是我的下一步计划，还没实现。"

实习生把没做的说成做了，是技术支持岗最大的扣分项——这个岗位天天要对客户讲真话。

## 四、三个高频追问的应答

**Q：为什么不让模型直接研判？**
> A：因为误处置和漏处置的代价不对称。我做过应急排查，一个错误的"这是挖矿"结论可能导致误杀业务进程；
> 一个错误的"这是正常"结论可能导致失陷扩大。模型的幻觉是概率性的，我不能把概率性风险放进判定环节。
> 让模型做翻译和表达，风险就可控了。

**Q：规则库怎么来的？会误报吗？**
> A：关键词来自公开威胁情报、ATT&CK 技术描述和我排查时见过的真实告警特征。
> 一定会误报——所以每条规则我都写了 `false_positive_hints`（比如"企业自建压测程序占用 CPU"会被挖矿规则误命中），
> 并且返回值里带上这些提示，让人工确认时有抓手。误报不可怕，可怕的是不知道哪里会误报。

**Q：为什么选 MCP 而不是自己写个 Agent？**
> A：MCP 是协议层，把能力和模型解耦。我现在这套规则引擎，换个模型、换个客户端都能直接用，
> 不用为每个模型重写一遍。而且 Server 侧不调模型，数据不出本机——这对安全场景很重要。
