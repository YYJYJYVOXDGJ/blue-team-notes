## 1. 体系总览：三层能力 + 一个支撑

主机安全不是一个「查杀」动作，而是一条能力链。任何一层缺席，其余两层都会失效：

```text
              ┌──────────── 治理支撑（Govern）────────────┐
              │ 授权与合规 · 制度与流程 · 职责与考核 · 度量  │
              └───────────────────────────────────────────┘
                                    │
   ┌────────────────┬────────────────┬────────────────┐
   │   预防 Prevent  │   检测 Detect   │   响应 Respond   │
   ├────────────────┼────────────────┼────────────────┤
   │ 资产与暴露面     │ 日志基建         │ 流程 SOP         │
   │ 身份与权限       │ 检测规则         │ 场景预案         │
   │ 配置基线         │ 主动狩猎         │ 工具与模板       │
   │ 补丁与漏洞       │ 情报驱动         │ 演练与复盘       │
   │ 数据与备份       │ 覆盖度度量       │ 恢复与加固       │
   └────────────────┴────────────────┴────────────────┘
        ↓ 没有预防              ↓ 没有检测              ↓ 没有响应
   永久的救火与重装        失陷长期无人发现        现场混乱、证据灭失
```

三层之间的关系是**成本递减、代价递增**：预防投入最小、检测次之、响应最贵。反过来，缺了预防就要靠检测兜，缺了检测就只能靠响应兜——而响应阶段每多花一小时，损失往往是指数级的。

### 1.1 预防层（Prevent）

目标：**让攻击者进不来、进不深、待不住。**

| 能力项 | 建设内容 | 落地物 |
|---|---|---|
| 资产与暴露面 | 资产清单与归属、端口服务基线、对外暴露面收敛、影子资产发现 | `*-hardening.md` 端口与服务章节 |
| 身份与权限 | 最小权限、特权账号隔离、MFA、堡垒机、账号生命周期 | `*-hardening.md` 账号章节 |
| 配置基线 | 操作系统与中间件基线、统一配置下发（GPO / Ansible / SCCM） | `linux-hardening.md`、`windows-hardening.md` |
| 补丁与漏洞 | 补丁节奏、应急补丁通道、漏洞扫描与修复闭环 | `*-hardening.md` 补丁章节 |
| 数据与备份 | **3-2-1 备份策略、离线/不可变备份、恢复演练** | 本文 §7 路线图（**待建设**） |
| 反持久化设计 | 关键路径只读化、启动项变更审计、白名单执行 | `*-attack-mapping.md` 权限维持清单 |

> 备份单独标出来：**勒索时代的最后一道防线不是 EDR，是离线可恢复的备份。** 没有经过恢复演练的备份等于没有备份。

### 1.2 检测层（Detect）

目标：**在攻击者完成目标之前发现他——理想是被拦，最差也要被记录。**

| 能力项 | 建设内容 | 落地物 |
|---|---|---|
| 日志基建 | 采集范围、字段完整性、留存周期、远端传输与防篡改 | `*-host-audit.md` 日志章节、`windows-detection-validation.md` §2.1 |
| 检测规则 | 规则来源（Sigma/EDR 内置/自建）、字段映射、误报治理 | `windows-detection-validation.md` §8 |
| 主动狩猎 | 假设驱动的狩猎、IOC 扫描、异常基线比对 | `*-attack-mapping.md` |
| 情报驱动 | 情报接入（IOC/TTP）、行业通报、厂商预警 | 本文 §9 |
| 覆盖度度量 | ATT&CK 覆盖矩阵、可见性缺口 | `*-attack-mapping.md` 覆盖度自评、本文 §6 |
| 检测验证 | 用例回归（回放/受控执行） | `windows-detection-validation.md` |

**一句真话**：检测能力的天花板由日志基建决定，不是由规则数量决定。规则再多，4104 没开就是看不见 PowerShell 无文件攻击。

### 1.3 响应层（Respond）

目标：**在最短时间内止血、保住证据、清干净、不再复发。**

| 能力项 | 建设内容 | 落地物 |
|---|---|---|
| 流程 SOP | 六阶段标准动作、角色分工、时限 | `ir-playbook.md` |
| 场景预案 | 按事件类型的具体打法 | `ir-scenarios.md` |
| 工具与模板 | IR 工具箱、模板文书 | `ir-templates.md`、`windows-forensics-toolchain.md`、`scripts/` |
| 演练 | 桌面推演、红蓝对抗、上机演练 | `ir-playbook.md` §0 |
| 复盘改进 | 根因分析、改进项闭环、规则与预案迭代 | `ir-playbook.md` §6 |

### 1.4 治理支撑（Govern）

制度性能力，往往被技术人员忽略，却是**出事时唯一能保护你的东西**：书面授权、事件分级与上报制度、数据保护与合规要求、跨部门协作机制、责任界定与考核。见 `DISCLAIMER.md`、`ir-templates.md`（授权书模板）、本文 §4 与 §5。

## 2. 与主流标准的对齐关系

体系设计不另起炉灶，直接对齐主流标准，这样对内能过审、对外能交代。

| 标准 / 框架 | 与本体系的关系 | 本仓库落点 |
|---|---|---|
| **NIST CSF 2.0** | 六大功能 Govern / Identify / Protect / Detect / Respond / Recover 构成本文 §1 的骨架 | §1、§3 |
| **NIST SP 800-61r3**（2025-04 发布） | 已按 CSF 2.0 重构，从「六阶段线性流程」转向「与风险管理融合」；本仓库 SOP 与其阶段划分对齐并保留 PICERL 可操作性 | `ir-playbook.md` |
| **ISO/IEC 27035** | 事件管理流程与成熟度模型，对应 IR 制度化 | `ir-framework.md` §4/§5 |
| **MITRE ATT&CK v16+** | 技术编号是全线文档的公共语言 | `*-attack-mapping.md` |
| **等保 2.0** | 主机层「安全计算环境」条款落地为基线核查项 | `*-hardening.md` |
| **法律合规** | 《网络安全法》《数据安全法》《个人信息保护法》《网络数据安全管理条例》决定上报义务与时限 | `ir-playbook.md` §7、`DISCLAIMER.md` |

> 说明：不同标准的阶段命名略有差异（PICERL / NIST / ISO）。本仓库统一采用 **准备 → 识别与分诊 → 遏制 → 取证与溯源 → 消除 → 恢复 → 复盘** 七段式，它同时兼容 PICERL 与 SP 800-61 的分期，且更贴合主机侧现场操作。

## 4. 组织与角色（RACI）

角色按团队规模可一人多岗，但**职责不能合并到同一个人**——尤其是「决策遏制」与「执行取证」，同一个人同时做会产生「为了取证耽误止血」或「为了止血毁掉证据」的偏差。

| 角色 | 定位 | 典型职责 |
|---|---|---|
| **L1 值班一线** | 7×24 监控与初判 | 告警初筛、首访、信息收集、按预案执行标准动作 |
| **L2 IR 二线** | 事件处置主体 | 分诊定级、遏制执行、主机取证、溯源分析 |
| **L3 专家三线** | 疑难与深度分析 | 恶意样本分析、内存取证、内核/驱动分析、攻击者画像 |
| **IMT 应急指挥组** | 决策层 | 定级裁决、业务中断取舍、资源协调、对外口径批准 |
| **业务方** | 系统负责人 | 提供业务上下文、确认影响面、配合停机与恢复验证 |
| **法务合规** | 法律风险控制 | 证据合法性、上报义务判定、对外承诺审查 |
| **公关 / 品牌** | 对外沟通 | 客户与媒体口径（**唯一出口**） |
| **HR** | 内部人员事件 | 内部人员违规、账号追责流程 |
| **外部支援** | 能力补充 | MDR/EDR 厂商、取证机构、监管与公安、保险 |

### 关键活动责任矩阵

R = 执行，A = 批准/担责，C = 被咨询，I = 被通知。

| 活动 | L1 | L2 | L3 | IMT | 业务方 | 法务 | 公关 |
|---|---|---|---|---|---|---|---|
| 告警初筛与首访 | **R** | C | — | I | I | — | — |
| 失陷判定与定级 | C | **R** | C | **A** | I | C | — |
| 遏制动作批准 | — | R | — | **A** | C | C | I |
| 主机取证与溯源 | I | **R** | C | I | C | C | — |
| 样本与内存深度分析 | — | C | **R** | I | — | — | — |
| 清除与恢复方案 | I | **R** | C | **A** | C | I | — |
| 业务恢复确认 | I | C | — | A | **R** | — | — |
| 上报监管 / 公安 | — | C | — | A | I | **R** | C |
| 对外通知客户 / 媒体 | — | — | — | A | I | C | **R** |
| 复盘与改进项闭环 | C | **R** | C | **A** | C | I | — |

**三条铁律**

1. **单一信息出口**：对外口径只有公关（或 IMT 指定发言人）能发，技术人员不单独对客户或媒体解释。
2. **法务前置**：涉及上报、赔偿、对外承诺、员工处理，先过法务。
3. **决策留痕**：每次遏制决策记录「谁、何时、依据什么、后果评估」（见 `ir-templates.md` 处置动作记录表）。

## 5. 事件分级与响应 SLA

分级的作用不是贴标签，而是**决定资源投入与决策层级**。分错级的代价：低级别误升导致业务无谓停机；高级别误降导致错过遏制窗口。

| 级别 | 判据 | 典型示例 | 响应时限 | 决策层级 |
|---|---|---|---|---|
| **P0 特别重大** | 核心业务中断 / 大规模数据泄露 / 勒索加密扩散中 / 触发法定上报义务 | 生产库被加密、核心系统全面不可用、百万级个人信息泄露 | **15 min 内启动**，2 h 内完成遏制 | IMT + 高层（CTO/CSO） |
| **P1 重大** | 单业务受影响 / 确认失陷且存在横向迹象 / 特权凭据泄露 | 一台生产机确认被控、域管密码泄露、对外服务被植入 Webshell | 30 min 内启动，4 h 内完成遏制 | IR 负责人 |
| **P2 一般** | 单主机可疑但无横向、无外带证据 | 挖矿进程、异常计划任务、可疑登录成功、边界设备告警 | 2 h 内启动，24 h 内闭环 | L2 IR |
| **P3 轻微** | 攻击失败 / 扫描 / 暴力破解未成功 / 疑似误报 | 大量 4625、端口扫描、EDR 低置信告警 | 1 个工作日内处置 | L1 值班 |

### 升级与降级规则

**立即升级（不等待、先升级后补判据）**

- 出现横向移动迹象（跨主机认证、远程管理工具落地）
- 出现数据外带迹象（大流量出向、云存储上传、压缩打包）
- 涉及域控、堡垒机、KMS、CI-CD、备份服务器等**信任锚点**
- 涉及对外服务或个人信息的泄露

**允许降级**

- 遏制完成且 24 h 无新增异常
- 根因明确、入口已修补、无遗留持久化
- 业务方确认影响面可控

**降级必须由原批准层级确认**，不允许执行层自行降级。

## 6. 度量指标

没有度量，就没有改进依据。指标要少而准，且**每个指标都要能被数据支撑**，否则会沦为填表作业。

| 指标 | 定义 | 计算口径 | 建议目标 |
|---|---|---|---|
| **MTTD** 平均检测时长 | 攻击发生 → 被发现 | 入侵时间（日志推断）→ 告警时间 | P1 事件 ≤ 24 h；理想 ≤ 4 h |
| **MTTA** 平均响应时长 | 告警 → 开始处置 | 告警产生 → 首个处置动作 | P0 ≤ 15 min；P2 ≤ 2 h |
| **MTTR** 平均恢复时长 | 开始处置 → 业务恢复 | 首动作 → 业务验证通过 | P0 ≤ 8 h；P1 ≤ 24 h |
| **Dwell Time** 驻留时长 | 入侵 → 清除完成 | 首次落地 → 最后持久化清除 | 逐季下降，目标 ≤ 72 h |
| **检测覆盖率** | ATT&CK 技术中被有效检测的比例 | DeTT&CT 或 `*-attack-mapping.md` 自评表 | 关键战术（持久化/凭据访问/横向）≥ 70% |
| **误报率** | 无效告警 / 总告警 | 需人工确认为误报的数量 | ≤ 30%，并持续下降 |
| **日志源完整率** | 应开且实测有数据的日志源比例 | `windows-detection-validation.md` §2.1 的 14 项 | **100%**（低于 100% 说明有盲区） |
| **预案有效性** | 已通过验证的预案比例 | 演练或实战验证通过数 / 预案总数 | ≥ 80% |
| **改进项闭环率** | 复盘中改进项按期完成比例 | 按期完成数 / 改进项总数 | ≥ 90% |

**特别注意两个「反向指标」**：告警总量下降不等于安全变好（可能是日志源掉了）；MTTR 变短不等于处置变强（可能是直接重装掩盖了溯源）。

## 7. 建设路线图

按「先止血、再建感知、后补治理」的顺序推进，避免一上来搞平台化。

### 0–30 天：止血与感知（最小可用）

- [ ] 把 §3 能力地图过一遍，标出**本环境实际缺失的日志源**（最大盲区通常在这里）
- [ ] 补开关键日志：Sysmon + 4104 + 4688 命令行 + 审核子类别；Linux 侧 auditd + journald 留存
- [ ] 日志留存期与容量核对，确保能覆盖一个完整处置周期（≥ 30 天）
- [ ] **备份可恢复性验证**：抽样恢复一台主机/一个库，记录实际耗时（这一步做了，勒索就没那么可怕）
- [ ] 跑 `scripts/*-ir-quickcheck.*` 建立主机基线快照，作为后续比对基准
- [ ] 落地 `ir-templates.md` 的授权书与联系人表（先让流程能启动）

### 30–90 天：流程与检测

- [ ] 按 `ir-playbook.md` 明确角色分工与升级路径，做**第一次桌面推演**
- [ ] 用 `windows-detection-validation.md` 做一轮检测验证，输出缺口清单
- [ ] 按缺口补规则，形成本环境的规则集并纳入版本控制
- [ ] 补齐 Linux 侧检测验证；建立狩猎假设库与月度狩猎节奏
- [ ] 加固落地：按 `*-hardening.md` 的 P0 项先改，走「审计 → 灰度 → 强制」

### 90–180 天：体系与度量

- [ ] 度量上线：MTTD / MTTA / MTTR / 日志源完整率进入月报
- [ ] 事件分级与上报制度成文，明确法定时限于责任人
- [ ] 演练机制常态化：桌面推演季度、上机演练半年
- [ ] 检测覆盖度量化（ATT&CK / DeTT&CT），把缺口变成可跟踪的改进项
- [ ] 云主机 / 容器 / K8s 应急补齐（见 `ir-scenarios.md` S8）
- [ ] 复盘机制闭环：每个 P1 以上事件产出一份复盘报告并跟踪改进项

## 9. 参考标准与最新技术跟踪

### 9.1 标准与方法论

- **NIST SP 800-61r3**（2025-04）：事件响应与 CSF 2.0 融合，取代 r2 的六阶段框架表述
- **NIST CSF 2.0**：新增 Govern 功能，把治理从隐含要求变成显式能力
- **ISO/IEC 27035-1/-2/-3**：事件管理流程与成熟度
- **MITRE ATT&CK**（持续更新，当前 v16 系列）：技术编号与检测映射的公共语言
- **MITRE D3FEND / DeTT&CT**：防御技术与检测覆盖度量化
- **等保 2.0**：主机层「安全计算环境」条款
- **CISA #StopRansomware Guide / 各类 IR Playbook**：可直接借鉴的场景化处置与遏制清单

### 9.2 技术栈跟踪（2024–2026）

| 方向 | 技术 / 工具 | 为什么值得跟 |
|---|---|---|
| 端点检测 | Sysmon + **Sigma 生态**（Chainsaw / Hayabusa / Zircolite） | 把社区数千条规则用到本地日志，成本最低的检测扩容方式 |
| Linux 运行时检测 | **eBPF 检测**（Falco、Tetragon）、auditd、`bpftrace` | 内核态可见性，弥补用户态日志被绕过的缺口 |
| 端点狩猎与响应 | **Velociraptor**、osquery、EDR/XDR 远程隔离 | 跨主机批量查询与实时响应，替代逐台登录 |
| 内存与无文件 | Volatility 3、MemProcFS、pe-sieve / **HollowsHunter** | 内存马与注入的唯一有效检出路径 |
| 取证分析 | **Eric Zimmerman 工具集**、KAPE、CyLR | 文件系统与执行痕迹时间线 |
| 对抗进化 | **BYOVD**（自带漏洞驱动卸 EDR）、EDR 免杀、合法远控滥用、C2 框架多元化（Sliver / Havoc / Brute Ratel） | 直接决定检测策略与日志留存，需持续跟踪 |
| 情报运营 | MISP、OpenCTI、STIX/TAXII | 把外部情报变成可检索的检测输入 |
| AI 辅助 | LLM 辅助日志归纳、告警摘要、狩猎假设生成 | 提速明显，但**必须人在回路**：不信任未经核实的结论，不上传敏感原始日志到外部服务 |
| 云原生 | 云审计（ActionTrail/CloudTrail）、K8s audit log、容器运行时安全 | 大量业务已上云，主机侧日志不足以覆盖 |

### 9.3 跟踪方式（建议固定动作）

- 订阅：厂商 IR blog（微软、CrowdStrike、Mandiant、WithSecure）、CISA 通报、ATT&CK 版本发布说明
- 规则源定期同步：SigmaHQ 规则库、各杀软/EDR 的检测规则更新
- 每季度做一次「体系自评」：回到 §3 能力地图与 §6 度量指标，看缺口是否收敛
