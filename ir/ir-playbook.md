## 0. 使用说明与三条底线

### 三条底线（任何阶段都不能破）

1. **先固定证据，再动手处置。** 处置动作本身会破坏证据：杀进程、删样本、重启、清日志。凡是「看一眼再决定」的直觉动作，先做记录（截图、哈希、导出日志）。
2. **能不动生产就不动生产，能精准就不搞一刀切。** 断网、停工、改密都是有业务代价的决策，必须由 §ir-framework.md 定义的决策层级批准，并记录依据。
3. **不清理发现的那一个后门就收工。** 对手通常会布置多个持久化点。清除必须以「持久化全量核对清单」为验收标准（见 `*-attack-mapping.md`）。

### 阶段与职责速览

| 阶段 | 目标 | 主责 | 关键输出物 |
|---|---|---|---|
| 准备 | 让流程能启动 | 安全建设/运维 | 预案、工具箱、授权、基线 |
| 识别与分诊 | 判断「是否失陷、多严重」 | L1 → L2 | 事件记录表、定级结论 |
| 遏制 | 止血，阻止扩散与外带 | L2（IMT 批准） | 遏制动作记录、隔离清单 |
| 取证与溯源 | 还原过程、找出入口与范围 | L2 / L3 | 时间线、溯源报告、证据交接单 |
| 消除 | 清除后门与入口 | L2 | 持久化核对清单（全部覆盖） |
| 恢复 | 安全地恢复业务 | L2 + 业务方 | 恢复验证清单、加严监控记录 |
| 复盘与改进 | 不再发生第二次 | L2（IMT 批准） | 复盘报告、改进项跟踪表 |

## 1. 准备（Preparation）

**目标**：事件发生前，把「要做决定的事」全部提前决定好，现场只做执行。

**输入**：无 ｜ **输出物**：预案、工具箱、授权书、基线快照、联系人表

### 1.1 制度与授权

- [ ] 应急预案成文并评审（本文即框架），明确分级标准与升级路径
- [ ] **《应急响应授权书》** 签署到位（模板见 `ir-templates.md`）——现场才能对生产系统做隔离、取证、停机
- [ ] 明确「紧急处置权限」：谁可以在什么条件下直接按 P0 标准动作，事后补批
- [ ] 与业务方约定停机窗口与代价评估口径（停机 1 小时的业务损失，需要提前知道）
- [ ] 法务介入点上墙：涉及上报、对外承诺、员工处理时必须法务前置

### 1.2 IR 工具箱（离线可用）

> 核心原则：**不使用失陷主机自带的工具做取证**。`ps`/`netstat`/`tasklist` 都可能被替换或 hook。

| 类别 | Windows | Linux | 说明 |
|---|---|---|---|
| 静态可信工具集 | Sysinternals 全套、`autorunsc64.exe`、`sigcheck` | **BusyBox 静态编译版**、静态 `lsof`/`ps`/`ss` | 放在只读介质，现场挂载执行 |
| 采集 | WinPmem、CyLR、KAPE、FTK Imager | avml、LiME、dc3dd | 内存与磁盘采集 |
| 分析 | Volatility 3、MemProcFS、EZ Tools、Chainsaw、Hayabusa | Volatility 3、Chainsaw（Linux 日志需转换） | 离线分析，不在原始盘上做 |
| 哈希校验 | `Get-FileHash`、`certutil -hashfile` | `sha256sum`、`md5sum` | **采集前后都算** |
| 网络 | `pktmon`、Wireshark（便携版） | `tcpdump`、`tshark` | 抓包留证据 |
| 隔离与阻断 | 防火墙策略脚本、EDR 隔离能力 | `iptables`/`nftables` 模板 | 事先测通，别现场现写 |
| 只读介质 | 空白 U 盘 ×2（一个放工具，一个存证据） | 同 | 证据盘贴标签封存 |

### 1.3 基线资产（最容易被跳过，但价值最高）

- [ ] 资产清单与责任人（含 IP、主机名、业务、所属环境）
- [ ] **主机基线快照**：跑 `scripts/linux-baseline-check.sh` / `scripts/windows-baseline-check.sh` 留档——事后「和之前比哪里变了」是最快的发现路径
- [ ] 正常业务进程/端口/计划任务/账号/SSH 公钥的白名单留档
- [ ] 日志源完整性确认：`windows-detection-validation.md` §2.1 的 14 项；Linux 侧 auditd/journald 留存与远端转发
- [ ] **备份可恢复性验证**：抽样恢复一台主机或一个库，记录实际耗时与步骤

### 1.4 演练机制

| 形式 | 频率 | 要点 |
|---|---|---|
| 桌面推演 | 每季度 | 用真实案例（如「域控被发现异常登录」）走一遍流程，重点是**决策与沟通**，不是技术 |
| 上机演练 | 每半年 | 在隔离环境复现一个场景，考「多久发现、多久遏制、证据齐不齐」 |
| 检测验证 | 每季度或规则变更后 | 按 `windows-detection-validation.md` 跑用例回归 |
| 恢复演练 | 每半年 | 真恢复一次，验证备份不是「看着有」 |

**演练评分维度**：发现时长（MTTD）、首动作时长（MTTA）、证据完整性、清除彻底性、沟通合规性、文案质量。

## 2. 识别与分诊（Identification & Triage）

**目标**：在最短时间内回答三个问题——**是否真失陷？影响多大？该定几级？**

**输入**：告警 / 监控 / 第三方通报 / 业务异常反馈 ｜ **输出物**：事件记录表、定级结论、升级决定

### 2.1 首访 15 分钟（收到告警后的标准动作）

按顺序做，**每一项都留档**：

```bash
# ── 第 1 步：确认时间基准（时间线错乱是最常见的取证事故）
date -u                                    # Linux
w32tm /query /status                       # Windows（确认 NTP 源与偏移）
```

```bash
# ── 第 2 步：谁在通信（先看网络，最快出线索）
# Linux
ss -tunap | grep -v '127.0.0.1'            # 或 /proc/net/tcp 直读（见 linux-host-audit.md 1.1）
# Windows
Get-NetTCPConnection -State Established | Select-Object LocalPort,RemoteAddress,RemotePort,OwningProcess
netstat -ano | findstr ESTABLISHED
```

```bash
# ── 第 3 步：可疑进程与父子关系（一次拿到链条）
# Linux
ps -ef --forest
ls -l /proc/*/exe 2>/dev/null | grep -E 'deleted|memfd'
# Windows
Get-CimInstance Win32_Process | Select-Object ProcessId,ParentProcessId,Name,CommandLine
```

```bash
# ── 第 4 步：近期落地文件（攻击者的手最常在这里露出来）
# Linux
find /tmp /var/tmp /dev/shm -type f -newermt '-3 days' -ls 2>/dev/null
# Windows
Get-ChildItem C:\Windows\Temp,$env:TEMP -Recurse -File -EA SilentlyContinue |
  Where-Object LastWriteTime -gt (Get-Date).AddDays(-3)
```

```bash
# ── 第 5 步：账号与登录（判断「谁进来过、从哪来」）
# Linux
last -aiF | head -30; grep -Ei 'Failed|Accepted' /var/log/secure | tail -30
# Windows
Get-WinEvent -FilterHashtable @{LogName='Security';Id=4624,4625,4648} -MaxEvents 60 |
  Select-Object TimeCreated,Id,@{n='User';e={$_.Properties[5].Value}},@{n='Type';e={$_.Properties[8].Value}},@{n='IP';e={$_.Properties[18].Value}}
```

```bash
# ── 第 6 步：日志源是否还活着（排除「检测失明」）
# 若某关键日志返回空 → 不是没攻击，是没数据
Get-WinEvent -LogName 'Microsoft-Windows-Sysmon/Operational' -MaxEvents 1
Get-WinEvent -LogName 'Microsoft-Windows-PowerShell/Operational' -MaxEvents 1
```

**一键化替代**：`scripts/linux-ir-quickcheck.sh` / `scripts/windows-ir-quickcheck.ps1` 已把上述动作打包为只读采集，现场优先跑脚本，再人工复核。

### 2.2 失陷判定的三档结论

| 结论 | 判据（满足任一） | 下一步 |
|---|---|---|
| **确失陷** | 存在无法用业务解释的持久化项（计划任务/服务/WMI 订阅/SSH 公钥）；样本文件落地并与外网通信；账号在非工作时段从异常 IP 登录成功；文件被加密 | 立即按 §2.3 定级并进入遏制 |
| **疑失陷** | 单条异常信号（可疑进程/异常外连/疑似 webshell 文件）但证据链不完整；日志缺失无法排除 | 加严采集、扩大狩猎范围，**限时**（如 4 小时）内给出结论 |
| **未失陷** | 经核查为业务行为或扫描/暴力破解未成功；有可信解释与留痕 | 记录结论与依据后关闭，同时检查是否**检测规则误报** |

> 「疑失陷」不允许无限期挂着。要么升级为确失陷，要么给出未失陷依据。悬而未决的事件是最危险的。

### 2.3 定级与升级

按 `ir-framework.md` §5 的分级表判定 P0–P3，然后：

- P0：**先启动、后补判据**。同时通知 IMT、业务方、法务，进入 §3
- P1：IR 负责人批准后进入 §3，并通知 IMT
- P2/P3：按标准动作处置，24 h / 1 工作日闭环

**立即升级信号**（不等判据完整）：横向移动迹象、数据外带迹象、涉及域控/堡垒机/备份服务器、涉及个人信息泄露。

## 3. 遏制（Containment）

**目标**：止血——阻止扩散、阻止外带、阻止进一步破坏。

**输入**：定级结论、影响范围初判 ｜ **输出物**：遏制动作记录、隔离清单、打蛇风险说明

### 3.1 先做决策：短遏制还是长遏制

这是整个响应过程中**最容易做错的一步**。盲目一刀切会打草惊蛇，让对手销毁痕迹或启动破坏逻辑；放任不管会让损失扩大。

| 情形 | 推荐策略 | 理由 |
|---|---|---|
| 单主机确失陷，无横向迹象 | **短遏制**：EDR 隔离（保留管理通道）或仅限制出向流量 | 精准，不惊动全局；保留观察窗口 |
| 确认横向移动（跨主机认证、批量远程工具） | **长遏制**：分段隔离 + 集中取证 + 凭据大规模重置 | 已扩散，必须按范围处置 |
| **勒索加密进行中** | **立即切断网络（物理/逻辑），但不要关机、不要重启** | 断电/关机可能触发引导加密或丢失内存中的密钥线索；内存里常常有解锁线索 |
| 数据外带进行中 | **精准切断出向通道**（比断全链路代价小），同时保留入向以便取证 | 目标是不让数据继续走，不是让业务全停 |
| APT 长期潜伏，尚在观察 | **长遏制**：加强监控为主，暂不动作；待摸清范围后一次性清除 | 打草惊蛇会让对手更换据点，前功尽弃 |
| 涉密/关键信息基础设施 | 由 IMT 决策，报监管后执行 | 有法定与行业处置要求 |

### 3.2 遏制动作候选（按影响面从小到大）

1. **精准阻断**：封单个出向 IP/域名/端口（防火墙、EDR 网络规则、DNS 黑洞）
2. **账号层**：禁用可疑账号、重置受影响账号口令、**踢出活动会话**（`logoff` / 撤销 token / 吊销证书）
3. **主机层**：EDR 网络隔离（保留控制通道）、ACL 限制、移出负载均衡
4. **网络层**：VLAN/ACL 隔离、黑洞路由、临时切断出口
5. **物理层**：拔网线（最后手段，注意可能触发失联告警与证据断点）

**每一项都必须记录**：谁批准、何时执行、影响了谁、如何回退。

### 3.3 打蛇风险评估（执行前必答）

- 对手会不会因此**销毁证据**或**启动破坏逻辑**（勒索加密、数据删除）？
- 对手会不会**更换据点**，导致我们正在追的线索断掉？
- 会不会**触发业务中断告警**，让事件外溢？
- 我们是否已经**掌握了足够的溯源信息**，可以承受线索断裂？

### 3.4 遏制阶段必须避免的动作

- 只隔离了主机、却没隔离对手的**其他控制通道**（如远程管理工具、VPN、云 AK）
- 隔离前**没有采集易失数据**（内存、连接、进程）——隔离后这些就没了
- 只改密码、**没有踢出会话**——已窃取的 token 仍然有效（这是极常见的漏洞）
- 只处理了入口主机，**没有处理横向到达过的其他主机**

## 4. 取证与溯源（Evidence & Analysis）

**目标**：还原「怎么进来的、做了什么、影响到哪」，为清除与恢复提供依据，并满足可能的合规与法律要求。

**输入**：隔离后的主机 ｜ **输出物**：时间线、溯源报告、证据交接单、持久化与横向清单

### 4.1 采集顺序（易失性优先，原则是「先做的不会毁掉后做的」）

```text
① 内存镜像 ──→ ② 网络连接 / ARP / 路由 ──→ ③ 进程与句柄 / 内核模块
      ──→ ④ 临时文件与临时账号 ──→ ⑤ 日志 ──→ ⑥ 磁盘镜像（最后）
```

**原因**：内存与运行态信息关机即失，磁盘相对持久。反过来做，就是「为了看磁盘把内存弄丢了」。

```bash
# ① 内存
# Linux
sudo avml /evidence/$(hostname)-mem.lime          # 或用 LiME
# Windows
WinPmem64.exe --output C:\evidence\mem.raw        # 注意输出到独立证据盘

# ② 网络
ss -tunap > /evidence/ss.txt; ip a > /evidence/ip.txt; ip route > /evidence/route.txt
arp -an > /evidence/arp.txt

# ③ 进程与内核态
ps -efww > /evidence/ps.txt
ls -l /proc/*/exe > /evidence/proc-exe.txt 2>/dev/null
lsmod > /evidence/lsmod.txt; ls /sys/module > /evidence/modules.txt
```

### 4.2 证据链（Chain of Custody）

凡涉及可能的追责、上报或司法程序，证据必须可证明「未被篡改」：

- [ ] **采集前后都计算哈希**（`sha256sum` / `Get-FileHash`），并记录到证据交接单
- [ ] 记录**原始介质信息**（主机名、序列号、采集时间、采集人、工具及版本）
- [ ] 采集到**写保护的独立证据盘**，贴标签、封存、登记
- [ ] 每次交接都签字，记录时间与用途（模板见 `ir-templates.md`）
- [ ] **不在原始介质上直接分析**——先做镜像副本，分析副本
- [ ] 统一时区（建议全程 UTC 记录，报告时再换算本地时间）

### 4.3 时间线重建

以「入口 → 立足 → 提权 → 持久化 → 横向 → 目标动作」为主线，把各来源证据归并到一条时间轴上：

| 来源 | Windows | Linux |
|---|---|---|
| 进程与命令行 | Sysmon 1、4688 | auditd EXECVE、`/proc`、bash history |
| 网络 | Sysmon 3/22、pktmon | conntrack、tcpdump、`/proc/net/*` |
| 文件落地 | Sysmon 11/15/23、USN | auditd PATH、`find -newermt`、`ls -l --time=*` |
| 持久化 | 7045、4698、Sysmon 19-21、13 | cron/`systemd` 文件 mtime、`authorized_keys` |
| 账号与登录 | 4624/4625/4648/4672/1149 | `last`/`lastb`、`secure`/`auth.log` |
| 痕迹清理 | 1102、104、EventRecordID 跳号 | 日志空洞、0 字节日志、`/var/log` mtime 异常 |

**时间戳伪造识别**：比对 `mtime`（修改）/ `ctime`（元数据变更）/ `btime`（创建，`stat -c %w` 或 `$STANDARD_INFORMATION`）是否自相矛盾——典型的伪造特征是「创建时间早于系统安装时间」或「ctime 晚于 mtime 很多」。

### 4.4 溯源要回答的六个问题

1. **入口点**：从哪进来的（弱口令、漏洞、钓鱼、VPN、第三方通道、供应链）？
2. **立足方式**：落地了什么（样本、Webshell、内存马、计划任务、服务、账号、公钥）？
3. **提权路径**：怎么拿到更高权限（漏洞、配置错误、凭据窃取）？
4. **持久化清单**：全部据点（**这是清除的验收标准**）
5. **横向范围**：到过哪些主机、用过哪些凭据、有没有动域控/堡垒机/云控制台？
6. **目标动作**：偷了什么、改了什么、破坏了什么、有没有外带通道？

### 4.5 常见分析陷阱

- **只信主机自带工具的输出** → 用静态可信工具交叉验证（`ps` vs `/proc` 差集、`ss` vs `/proc/net/tcp` 差集）
- **只看日志、不看状态** → 无文件攻击在日志里可能完全干净，必须配合内存与进程态
- **把「日志没有」当成「没发生」** → 先确认日志源是否开启、是否被清理
- **时间线只用本机时间** → 多主机事件必须统一时区，并校验各主机时钟偏移

## 5. 消除（Eradication）

**目标**：把对手彻底赶出去，且不留下「第二个后门」。

**输入**：持久化清单、横向清单、入口点结论 ｜ **输出物**：持久化全量核对清单（逐项打勾）、入口修补记录

### 5.1 清除 vs 重装：决策树

```text
是否存在内核级/驱动级后门（rootkit、恶意驱动、hook）？
├── 是 ──────────────────────────────→ 重装（不要试图在线清除）
└── 否
    ├── 是否有凭据泄露（密码哈希/明文/令牌/证书）？
    │   ├── 是 ── 业务可停机 ──→ 重装 + 全量凭据重置
    │   └── 是 ── 业务不可停机 ──→ 最小清除 + 全量凭据重置 + 加严监控
    └── 否
        ├── 业务可停机 ──→ 优先重装（成本更低、更彻底）
        └── 业务不可停机 ──→ 最小清除 + 逐项核对持久化 + 长期监控
```

**判断依据不是「能不能清干净」，而是「能否承担清不干净的后果」。**

### 5.2 清除动作（必须按全量核对清单执行）

先看 `linux/linux-attack-mapping.md` 与 `windows/windows-attack-mapping.md` 里的**权限维持全量核对清单**，逐项打勾。核心要点：

| 平台 | 必须核对的据点 |
|---|---|
| Linux | `~/.ssh/authorized_keys`（所有用户）、crontab（所有用户）、`/etc/cron.*`、systemd unit（含 timer）、`/etc/ld.so.preload`、PAM 模块、`/etc/rc.local`、profile.d、内核模块、SUID 异常、UID 重复账号、空密码账号 |
| Windows | Run/RunOnce、服务（含 ServiceDll/FailureCommand）、计划任务（含隐藏任务与 TaskCache）、**WMI 事件订阅三件套**、IFEO、SilentProcessExit、Winlogon/AppInit、LSA 认证包、COM 劫持、Netsh Helper、BITS、ADS、本地账号与管理员组、组策略启动脚本、WSL 侧 |

**清除顺序建议**：先修入口（堵住再进的路）→ 再清持久化（断掉再起的路）→ 最后清账号与凭据（断掉再用的路）。

### 5.3 凭证与信任锚点重置

- [ ] 所有受影响账号改密（**先确认横向范围再执行，避免打草惊蛇与大面积业务中断**）
- [ ] 特权账号（域管、堡垒机、云 AK/SecretKey、KMS、CI-CD 凭据）全部轮换
- [ ] 撤销活动会话、吊销证书、失效 token（仅改密码不够）
- [ ] 检查并清理：SSH 公钥、API Key、应用内嵌凭据、配置文件中的明文口令
- [ ] 服务账号（数据库、中间件、备份）也要覆盖

### 5.4 入口修补（否则一定复发）

- [ ] 打补丁 / 升级受影响组件
- [ ] 关闭被利用的暴露面（端口、接口、调试端点、默认口令、未授权访问）
- [ ] 修改配置基线（按 `*-hardening.md` 整改发现的问题）
- [ ] 对外服务加 WAF/防护规则，并验证规则确实生效

## 6. 恢复（Recovery）

**目标**：在可验证的前提下恢复业务，且**不把攻击者一起恢复回来**。

**输入**：清除完成确认、备份可用性 ｜ **输出物**：恢复验证清单、加严监控记录

### 6.1 恢复顺序

```text
① 外围先起（DNS/负载均衡/网关）→ ② 中间件与数据库 → ③ 应用 → ④ 核心业务
```

原因：外围先起、核心后起，可以在小流量下暴露问题，避免核心被二次打穿。

### 6.2 恢复来源的选择

| 来源 | 适用 | 风险 |
|---|---|---|
| 重装 + 配置回补 | 主机被控、rootkit、凭据泄露 | 配置回补可能带回旧漏洞，必须按新基线 |
| 备份恢复 | 数据被破坏/加密 | **必须确认备份时间点早于入侵时间**，否则把木马一起恢复 |
| 在线修复 | 影响面小、业务不可停 | 必须逐项验证持久化已清 |

> **红线**：恢复任何一个来源之前，先确认它的时间点早于**入口点时间**。这条不确认，恢复就是二次投毒。

### 6.3 恢复验证清单

- [ ] 业务功能与性能验证（业务方签字确认）
- [ ] 安全配置回补到加固基线（不是恢复旧配置）
- [ ] 无新增持久化项（再跑一遍持久化核对清单）
- [ ] 无异常外连（观察窗口内 `ss`/`netstat` 无异常出向）
- [ ] 日志采集与告警已恢复并确认有数据
- [ ] 备份任务已恢复正常且成功一次

### 6.4 加严监控期（至少 14 天）

事件闭环不代表可以撤防。对手在清除后常会尝试**回来**（用还没轮换的凭据、或未发现的通道）。

加严期重点监控：

| 监控项 | 具体指标 |
|---|---|
| 相同入口的访问 | 曾利用的漏洞/路径/账号是否再次出现 |
| 相同手法特征 | 曾用过的持久化位置、样本哈希、C2 域名/IP |
| 同类异常 | 异常时间段登录、异常进程链、异常出向流量 |
| 日志异常 | 日志源是否再次出现空洞、清日志事件 |

## 7. 复盘与改进（Post-Incident）

**目标**：把一次事件变成组织能力的提升，而不是「处理完了就翻篇」。

**输入**：全过程记录 ｜ **输出物**：复盘报告、改进项跟踪表、更新的规则与预案

### 7.1 复盘会议结构（建议 90 分钟）

| 环节 | 时长 | 内容 |
|---|---|---|
| 事实陈述 | 20 min | 按时间线复述客观事实（**不评价、不追责**） |
| 数据复盘 | 20 min | MTTD / MTTA / MTTR / 驻留时长与目标对比 |
| 根因分析 | 25 min | 5 Whys 或鱼骨图，区分「技术根因」与「管理根因」 |
| 改进项生成 | 20 min | 每项必须有责任人 + 时限 + 验收标准 |
| 结论与归档 | 5 min | 定稿复盘报告，明确跟踪机制 |

**原则**：复盘对事不对人。追责会让人隐瞒细节，而细节恰恰是唯一有价值的部分。

### 7.2 必须回答的问题

- 为什么没早发现？（是没日志、没规则、还是规则没告警？）
- 为什么影响这么大？（预防层哪一项失效了？）
- 遏制是否及时？（决策是否被流程卡住？）
- 证据是否齐全？（能否支撑上报与追责？）
- 清除是否彻底？（有没有第二次检查？）
- 沟通是否合规？（上报时限是否满足？）

### 7.3 改进项的三条要求

1. **可验证**：不能是「加强管理」，必须是「8 月底前为全部生产主机开启脚本块日志，抽查 10 台确认有数据」
2. **有责任人**：具体到岗位，不写「相关部门」
3. **有迭代回路**：涉及检测规则的，回到 `windows-detection-validation.md` 的用例集做回归；涉及预案的，更新 `ir-scenarios.md` 对应章节

## 8. 专项：沟通与上报

### 8.1 沟通矩阵

| 对象 | 内容 | 时机 | 责任 |
|---|---|---|---|
| IMT / 管理层 | 影响面、已做动作、需要什么决策 | 定级后立即，之后每 2 h 一次 | IR 负责人 |
| 业务方 | 业务影响、预计恢复时间 | 确认影响面后 | IR 负责人 |
| 法务合规 | 是否触发上报义务、证据合法性 | 定级后立即 | IR 负责人 |
| 监管 / 公安 | 按法定格式与时限报告 | 满足触发条件即刻 | 法务 + IMT |
| 客户 / 用户 | 统一口径的告知 | **公关统一出口** | 公关 |
| 全体员工 | 防范提示（如钓鱼事件） | 视情况 | 公关 + IT |
| 外部厂商 | 技术支持、样本提交 | 需要时 | L3 |

### 8.2 上报触发与时限

> **重要提示**：以下为流程设计参考，**具体适用范围与时限以最新法律法规、行业监管规定及属地要求为准**，最终由法务判定。

| 法规 / 规定 | 触发情形 | 时限与要求 |
|---|---|---|
| 《网络安全法》 | 发生个人信息泄露、毁损、丢失 | 立即补救，告知用户并向主管部门报告 |
| 《数据安全法》 | 发生数据安全事件 | 立即处置，按规定告知用户并向主管部门报告 |
| 《个人信息保护法》 | 个人信息泄露、篡改、丢失 | 立即补救，通知履职部门与个人 |
| 《网络数据安全管理条例》 | 发生数据安全事件 | 立即启动预案处置，并在事件发生后 **24 小时内**向主管部门报告 |
| 公安网络安全报告要求 | 发生网络安全事件 | 通常要求在 **24 小时内**向属地公安机关报告 |
| 行业监管（金融/能源/医疗等） | 重大事件 | 行业规定往往**更短**（如重大事件 2 小时内初报），按行业规定执行 |

**流程**：定级 P0/P1 → 法务判定上报义务 → 按格式准备材料 → IMT 批准 → 按规定渠道提交 → 留档回执。

### 8.3 对外话术六条原则

1. **只讲事实与已确认信息**，不猜测攻击者身份与动机
2. **不承诺**「数据未泄露」「已完全恢复」等未经证实结论
3. **不指责**第三方或内部人员
4. **不提供**技术细节（避免二次被利用，也避免被追问）
5. **单一出口**：所有对外沟通由指定发言人统一发布
6. **同步留痕**：所有对外沟通内容留档备查

## 9. 专项：多平台与多机协同

### 9.1 双平台差异（避免照搬）

| 维度 | Windows | Linux |
|---|---|---|
| 首要痕迹源 | Sysmon、Security 日志、Prefetch/Amcache、注册表 | auditd、journald、`/proc`、文件 mtime |
| 对抗检测 | 多源进程交叉验证、驱动/签名核查 | `/proc` 直读绕工具替换、`ld.so.preload` 核查 |
| 持久化主战场 | 注册表 + 服务 + WMI 订阅 + 任务计划 | cron + systemd + SSH 公钥 + 动态链接 |
| 常见盲区 | 4688 无命令行、4104 未开、任务计划 Operational 未开 | auditd 未配规则、日志被清无痕迹、容器内不可见 |

### 9.2 多机协同要点

- **统一时区与时钟**：所有主机校时，取证统一 UTC
- **横向链路图**：以「登录事件（源 IP → 目标）+ 远程服务 + 凭据使用」画图，标出必经节点（域控、堡垒机、跳板机）
- **信任锚点优先**：域控、堡垒机、KMS、CA、CI-CD、备份服务器一旦涉及，直接升级 P1/P0
- **批量处置要分批**：先处置外围与已确认主机，再处理可疑主机，避免一次性大规模动作导致业务中断
- **信息汇总单一**：指定一人维护事件时间线（单一事实来源），避免多头记录冲突

## 附录 B：现场禁忌清单

| # | 禁忌动作 | 后果 |
|---|---|---|
| 1 | 发现异常先关机 / 重启 | 丢失内存证据；勒索场景可能触发引导加密 |
| 2 | 先杀进程再分析 | 丢失进程树、句柄、已加载模块等关键证据 |
| 3 | 直接删除发现的恶意文件 | 失去样本，无法分析入口与家族 |
| 4 | 用失陷主机的工具做取证 | 工具可能已被替换/hook，结论不可信 |
| 5 | 在原始磁盘上直接分析 | 破坏证据可用性，法律上可能不被采纳 |
| 6 | 清理或覆盖日志 | 自毁证据，且可能构成合规问题 |
| 7 | 只改密码不踢会话/不吊销令牌 | 攻击者凭已窃取凭据继续可用 |
| 8 | 只清除已发现的据点 | 对手其他据点存活，往往数日内复发 |
| 9 | 未确认横向范围就全网统一改密 | 打草惊蛇 + 大面积业务中断 |
| 10 | 溯源未完成就恢复业务 | 把攻击者一起恢复回来，二次失陷 |
| 11 | 恢复备份时不核对备份时间点 | 恢复出被植入的系统 |
| 12 | 技术人员直接对客户/媒体解释 | 口径失控，法律与商业风险 |
| 13 | 「疑失陷」无限期悬置 | 错过遏制窗口，最终以更大代价暴露 |
| 14 | 事件闭环后立即撤防 | 对手回归无人发现 |
