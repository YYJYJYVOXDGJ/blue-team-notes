## T1 应急响应授权书

> 用途：赋予处置团队对指定系统实施隔离、取证、停机等操作的权限。**没有这份文书，现场就没有合法的处置依据**，且事后难界定责任。

```text
                        应急响应授权书

授权方（甲方）：【组织名称】
处置方（乙方）：【安全团队 / 部门 / 外部服务机构】

一、授权事项
  甲方因【事件简述，如：2026 年 9 月 18 日发现某主机存在可疑外连】，
  授权乙方对下列系统实施应急处置，具体授权范围如下：

  1. 授权系统范围
     - 主机/系统：【主机名、IP、业务系统名称】
     - 环境：□生产  □测试  □办公  □云环境【账号/区域】
     - 涉及数据范围：【系统/数据库名称】

  2. 授权操作范围（勾选项）
     □ 读取系统日志、进程、网络连接、文件等信息
     □ 采集内存镜像与磁盘镜像
     □ 导出并分析业务数据与配置文件
     □ 对目标主机实施网络隔离（EDR 隔离 / 防火墙策略 / 断网）
     □ 暂停、禁用可疑账号与访问凭据
     □ 重启或停止指定服务、进程
     □ 暂停相关业务对外服务
     □ 变更或重置账号口令、密钥、证书
     □ 删除或清除已确认的恶意文件与持久化项
     □ 其他：【补充】

  3. 明确排除的操作（不授权范围）
     - 【如：不得删除生产数据库数据；不得更改业务配置；不得中断结算系统】

二、授权时限
  生效时间：【YYYY-MM-DD HH:MM】
  失效时间：【YYYY-MM-DD HH:MM】或「至事件处置结束并由甲方书面确认」

三、双方责任
  1. 乙方应按授权范围操作，超出范围须事先取得甲方书面同意；
  2. 乙方应对接触到的甲方数据、日志、个人信息承担保密义务；
  3. 乙方应在处置结束后提交事件报告与处置记录；
  4. 因紧急遏制需要、且已尽合理告知义务的处置动作，不视为越权；
  5. 甲方应提供必要的系统信息、账号权限与业务配合。

四、批准与确认
  甲方授权代表（签字）：____________  职务：________  日期：________
  甲方业务责任人（签字）：____________  职务：________  日期：________
  乙方项目负责人（签字）：____________  日期：________
  （如涉及监管、法务要求，法务/合规会签：________  日期：________）

  备注：紧急情况下可先以邮件/即时通讯达成授权，事后 24 小时内补签本文件。
```

```text
  发现方式：□ 告警  □ 监控  □ 业务反馈  □ 外部通报  □ 主动狩猎  □ 其他

  是否升级过：□ 否  □ 是 → 【原级别 → 新级别，升级原因，时间】

  | | | | |

七、证据清单
```

## T3 现场证据交接单

> 用途：**Chain of Custody（证据链）**。涉及上报、追责或司法程序时，这份单据决定证据是否可被采信。

```text
                       证据交接单

证据编号：EVD-【YYYYMMDD】-【序号】

一、证据基本信息
  证据类型：□ 内存镜像  □ 磁盘镜像  □ 日志导出  □ 恶意样本
            □ 配置文件  □ 截图/录屏  □ 网络抓包  □ 其他【】
  关联事件编号：INC-【】
  来源设备：主机名【】 IP【】 序列号/资产编号【】
  采集时间：【YYYY-MM-DD HH:MM】（时区【】）

二、采集信息
  采集工具及版本：【，如 WinPmem 4.0 / avml 0.14 / wevtutil】
  采集方式：□ 在线采集  □ 离线（拆盘/引导）  □ 远程镜像
  存储介质：型号【】 序列号【】 容量【】
  是否写保护：□ 是  □ 否 → 说明：【】

三、完整性校验
  | 校验算法 | 采集前哈希 | 采集后哈希 | 是否一致 |
  |---|---|---|---|
  | SHA256 | | | □ 一致 □ 不一致 |
  | MD5（如需要） | | | |

  说明：内存镜像等流式证据无「采集前哈希」，以采集后哈希 + 采集过程记录为准。

四、交接记录（每一次交接都要登记）
  | 序号 | 交接时间 | 交出人 | 接收人 | 交接原因/用途 | 证据状态（封存/启用） | 签字 |
  |---|---|---|---|---|---|---|
  | 1 | | | | | | |
  | 2 | | | | | | |

五、保管与使用要求
  1. 证据介质须封存并标注编号，存放于【安全位置】；
  2. 分析应在镜像副本上进行，原始介质不得直接操作；
  3. 启用原始介质须经【批准人】批准并登记；
  4. 证据销毁须经【批准人】批准，并保留销毁记录。

  填表人：________  审核人：________  日期：________
```

## T4 处置动作记录表（决策留痕）

> 用途：记录「谁、何时、依据什么、做了什么事、后果如何」。既用于复盘，也用于**事后免责与责任界定**。

```text
                       处置动作记录表

事件编号：INC-【】

| 序号 | 时间(UTC) | 执行人 | 动作内容 | 动作类型 | 批准人 | 决策依据 | 影响范围 | 可回退性 | 实际结果 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | | | 例：对 10.x.x.21 实施 EDR 网络隔离 | 遏制 | | 该主机确认外连 C2 | 单主机，不影响业务 | 可随时解除 | 隔离成功，外连中断 |
| 2 | | | 例：重置账号 svc_backup 口令并踢出会话 | 遏制 | | 该账号在 3 台主机异常登录 | 备份任务需重新配置 | 需重新下发凭据 | 备份任务已更新，恢复正常 |
| 3 | | | | | | | | | |

动作类型：遏制 / 取证 / 清除 / 恢复 / 加固 / 沟通

重要决策补充说明（用于解释「为什么当时这样做」）：
  决策场景：【如：是否立即清理发现的 1 个后门，还是先观察】
  备选方案：【】
  选择理由：【如：仅发现 1 处据点，横向范围未明，立即清理会打草惊蛇】
  风险与接受的代价：【】
  决策人 / 时间：【】
```

```text
四、初步判断
  可能入口：【】
  当前级别：□ P0  □ P1  □ P2  □ P3

五、下一步计划与需要的支持
  【】

六、待确认事项
  【，如：影响范围、是否存在数据外带、是否需要上报监管】
```

### T5.2 续报（每 2 小时或阶段完成时）

```text
                       网络安全事件续报

事件编号：【】           报告时间：【】

一、进展概述
二、影响面更新（新增受影响系统/账号/数据）
三、已完成动作及效果
四、当前阶段与预计完成时间
五、风险与阻塞（什么在阻碍处置，需要谁支持）
六、需要决策的事项
  | 事项 | 建议方案 | 需谁批准 | 期望答复时限 |
```

### T5.3 结报（事件闭环时）

```text
                       网络安全事件结报

事件编号：【】           报告时间：【】

一、事件概况（一段话讲清：何时、何系统、怎么进来的、造成什么后果）
二、时间线（发现 → 遏制 → 清除 → 恢复的关键时间点）
三、根因分析
  技术根因：【如对外服务未修补漏洞 / 未强制 MFA】
  管理根因：【如日志源未开启，导致驻留 X 天未被发现】
四、影响评估
  业务影响：【】
  数据影响：【类型、规模、是否涉及个人信息、是否上报】
五、处置措施与效果
六、清除彻底性验证
  □ 持久化核对清单已全量覆盖  □ 无新增异常外连  □ 凭据已全量轮换
七、遗留风险与后续计划
八、结论与责任界定（如需要）
```

## T8 通知模板（对内 / 对客户 / 对员工）

> 原则：**只讲已确认的事实**，不猜测攻击者身份与动机，不承诺未经证实的结论，不提供技术细节，单一出口发布。

### T8.1 对内通告（给管理层/业务方）

```text
【事件进展通告】

事件编号：INC-【】        发布人：【】        时间：【】

1. 现状：截至【时间】，【简述事实：哪些系统受影响、业务是否可用】
2. 已处置：【已采取的动作】
3. 影响与风险：【对业务、客户、数据的影响，以及尚不确定的部分】
4. 需要配合：【业务方需配合事项，如确认恢复验证、提供系统信息】
5. 下一步与时间点：【】
6. 信息口径：对外沟通由【公关/发言人】统一发布，其他人员不单独对外解释。
```

### T8.2 对客户/用户通知（须经法务与公关审核）

```text
【关于服务异常的说明】

尊敬的客户：

【时间】，我们监测到【系统】出现异常。经初步调查，【已确认的事实陈述】。
我们已于【时间】采取了【处置措施】，当前【服务状态说明】。

为保护您的账号安全，建议您：
```
